# 시스템 테이블 경계 이상 감사 — 번역 배치 0001–0002

## 범위와 정책

- 대상: `batch_0001.jsonl`, `batch_0002.jsonl`에 속한 승인 번역 중 구조화 시스템 테이블과 직접 일치하지 않았던 TM 61건
- 번역 및 문구 판단: **Codex 내부 모델의 추론만 사용**
- 외부 번역 모델/API: **사용하지 않음**
- 기존 reviewed 배치 및 `translation_memory_draft.json`: **수정하지 않음**
- 기계 판독 결과: `batches_0001_0002.json`

## 감사 방법

1. 각 TM의 모든 `occurrence_id`를 `text_catalog.json`에서 역참조했다.
2. NUL 스캐너의 `[offset, offset + byte_length)` 범위와 동일 스키마의 구조화 테이블 필드 바이트 범위를 비교했다.
3. **offset 범위가 정확히 한 필드와 겹치는 경우만** 연결했다. 문자열 부분 일치만으로는 확정하지 않았다.
4. 스캐너 바이트와 필드 바이트를 각각 카탈로그의 `source_path` 원본에서 다시 읽어 `raw_hex`와 일치하는지 검증했다.
5. 구조 바이트가 번역 앞에 복사된 경우 그 접두부만 제거했고, 스캐너가 실제 첫 글자를 누락한 8건은 구조화 필드 원문을 기준으로 뜻을 복구했다.
6. 정리된 한국어를 현행 `canonical_v1/codebook.json`으로 인코딩하고, 필드 용량에서 NUL 1바이트를 제외한 실제 허용 길이와 비교했다.

## 대표적인 구조 바이트 혼입 증거

- `todo:104:lead`: 스캐너 `0x3A8D`, 실제 필드 `0x3A90`. 앞의 `0E0A3C`가 `<$0E>\n<`로 잘못 붙었다.
- `help:295:title`: 스캐너 `0x18FDB`, 실제 필드 `0x18FDD`. 앞의 `6020`이 `` ` ``와 공백으로 잘못 붙었다.
- `chat:188:title`: 스캐너 `0x76F6`, 실제 필드 `0x76F8`. 앞의 `013F`가 `<$01>?`로 잘못 붙었다.
- `magic:13:menu_name`: 스캐너 `0x853`, 실제 필드 `0x854`. 앞의 `2D`가 `-`로 잘못 붙었다.

각 61건의 전체 offset, raw hex, source SHA-256, scanner↔table 시작점 차이, 겹친 바이트 수는 JSON의 `evidence`에 기록했다.
