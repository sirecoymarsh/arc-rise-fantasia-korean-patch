## WTMD 구조

`EUC28-0.wtm`부터 `EUC28-8.wtm`까지 아홉 파일의 구조가 모두 같다.

| 항목 | 값 |
|---|---:|
| 파일 크기 | 262,208 bytes (`0x40040`) |
| 매직 | `WTMD` |
| 팔레트 오프셋 | `0x20` |
| 이미지 오프셋 | `0x40` |
| 이미지 크기 | 262,144 bytes (`0x40000`) |
| 이미지 크기 | 512 × 1024 |
| GX 포맷 | `C4` / CI4 (`0x08`) |
| 팔레트 | RGB5A3 16색 (`0x02`) |
| GX 타일 | 8 × 8, 한 바이트에 high/low nibble 두 픽셀 |

각 페이지의 RGB5A3 팔레트는 같은 계열의 검정 알파 단계와 불투명 회색 단계지만 **인덱스 순서가 조금씩 다르다**. 따라서 주입기는 페이지별 원본 팔레트를 그대로 읽어 양자화한다. 헤더와 팔레트는 수정하지 않는다.

작성한 Python 디코더 결과는 별도 PowerShell 디코더인 `work/arf_format_research/EUC28-0.png`와 픽셀 단위로 완전히 일치했다.

## 글리프 셀과 주소 매핑

텍스처의 실제 글리프 격자는 다음과 같다.

- 셀: **22 × 28 px**
- 페이지당: **23열 × 36행 = 828셀**
- 사용 영역: 506 × 1008 px
- 우측 6 px와 하단 16 px는 셀 영역 밖 여백
- 전체 물리 용량: 828 × 9 = **7,452셀**

아홉 WTM은 하나의 가상 슬롯 스트림처럼 이어진다.

```text
page       = global_slot // 828
local_slot = global_slot % 828
x          = (local_slot % 23) * 22
y          = (local_slot // 23) * 28
```

일본어 2바이트 코드에서 가상 슬롯으로 가는 규칙은 다음과 같이 확인됐다. 각 행은 94개 코드 외에 2개 패딩을 두어 96칸 간격으로 배치된다.

```text
A1A1..A8FE: global_slot = 1   + (lead - A1) * 96 + (trail - A1)
B0A1..F4FE: global_slot = 721 + (lead - B0) * 96 + (trail - A1)
```

`A9..AF` 행은 글꼴 주소 공간에서 생략된다. `A8` 상자문자 영역 다음에 `B0` 한자 영역이 `global_slot=721`에서 시작한다.

검증 랜드마크:

| 바이트 | 글자 | global | 페이지 | local | 좌표 |
|---|---|---:|---:|---:|---:|
| `A1A2` | 、 | 2 | 0 | 2 | 44, 0 |
| `A3B0` | ０ | 208 | 0 | 208 | 22, 252 |
| `A4A1` | ぁ | 289 | 0 | 289 | 286, 336 |
| `A5A1` | ァ | 385 | 0 | 385 | 374, 448 |
| `A6A1` | Α | 481 | 0 | 481 | 462, 560 |
| `A7A1` | А | 577 | 0 | 577 | 44, 700 |
| `A8A1` | ─ | 673 | 0 | 673 | 132, 812 |
| `B0A1` | 亜 | 721 | 0 | 721 | 176, 868 |
| `B1A1` | 院 | 817 | 0 | 817 | 264, 980 |
| `B1AC` | 卯 | 828 | 1 | 0 | 0, 0 |
| `F4A6` | 熙 | 7,254 | 8 | 630 | 198, 756 |

`B1AC`가 정확히 `EUC28-1.wtm` 첫 셀로 넘어가는 것이 페이지 연속성의 강한 증거다. 전체 주소표는 `euc_slot_map.json`에 저장했다.

`F4A6` 뒤에도 8번 페이지에 확장 글리프와 ASCII/가나 계열 글리프가 남아 있다. 이 영역은 표준 Python `euc_jp`로 설명되지 않는 게임/벤더 확장 또는 별도 렌더링용 영역일 수 있으므로 그대로 보존해야 한다.

## 한국어 글리프 주입 전략

### 권장 계약

1. 번역문을 UTF-8 한국어로 관리한다.
2. 빌드 시 한글 음절/자모마다 전용 2바이트 글리프 ID를 배정한다.
3. 텍스트에는 Unicode나 CP949를 직접 넣지 않고 코드북의 2바이트 값을 넣는다.
4. 폰트에는 같은 코드북 좌표에 대응 한글 글리프를 넣는다.
5. `A1..A8`의 문장부호, 숫자, 라틴 문자, 화살표 등은 원본을 보존한다.
6. 한글은 `B0A1..F4FE` 영역에서 배정한다. 이 영역에는 총 **6,486개** 2바이트 코드가 있어 실제 번역 코퍼스에 필요한 고유 한글 음절 수를 충분히 수용할 가능성이 높다. 현대 한글 11,172자를 전부 넣는 방식은 용량을 초과하므로 코퍼스 기반 부분집합을 써야 한다.

### 코드북 안정성

- 최초 생성 시 필요한 한글을 Unicode 순으로 배정한다.
- 이후에는 기존 배정을 움직이지 않고 새 글자만 뒤에 추가하는 **append-only** 방식으로 유지한다.
- `arf_euc28_mapping.py codebook --existing ...`가 이를 지원한다.
- 부분 한국어화/파일럿 단계에서는 아직 남아 있는 일본어가 깨지지 않도록 원문 코퍼스의 일본 한자 코드와 raw 코드쌍을 예약해야 한다.
  - `--reserve-text`: UTF-8 원문에서 EUC-JP 한자쌍 예약
  - `--reserve-hex`: 카탈로그에서 추출한 raw `B0A1..F4FE` 쌍 예약
- 완전 한국어판에서도 엔진 fallback, 숨은 디버그/오류문, 미추출 표면에 사용되는 원문 글리프는 예약하는 편이 안전하다. 용량이 부족할 때만 실제로 더 이상 참조되지 않는 일본어 슬롯을 증거 기반으로 회수한다.

### 셀 렌더링

- 고정 셀 폭 22 px, 높이 28 px를 유지한다. 한국어 한 글자도 원문 전각 문자처럼 2바이트/1셀이다.
- 샘플은 `C:\Windows\Fonts\malgunbd.ttf`, 22 px를 사용했다. 폰트 SHA-256은 `e8cbc0b2afcc14fb45dfb6086d5102c0b23a96e7b6e708f3122acde1b86c9082`이다.
- 실제 릴리스는 선택 글꼴 파일 해시와 크기를 빌드 매니페스트에 고정해야 한다.
- 주입기는 4배 해상도에서 글리프와 1 px 외곽선을 렌더링하고, 각 페이지 원본 RGB5A3 팔레트에 양자화한 뒤 전체 CI4 텍스처를 다시 타일링한다.
- 실제 게임 셰이더/배경에서 명도, 외곽선, 기준선이 달라질 수 있으므로 메뉴와 대화창에서 Dolphin 캡처로 크기·명도·클리핑을 조정해야 한다. 샘플은 포맷/매핑 가능성 확인용이다.

## 자동 검증 결과

`validation.json` 기준:

- 원본 WTM 9개 모두 decode → encode 결과가 바이트 단위 동일: **통과**
- 11개 EUC/슬롯/페이지/좌표 랜드마크: **전부 통과**
- 샘플 주입 후 모든 WTM 파일 크기 유지: **통과**
- 샘플 주입 후 헤더/팔레트 보존: **통과**
- 샘플 주입본 재디코드 인덱스가 주입 버퍼와 동일: **통과**
- 변경되지 않은 1~8번 페이지는 원본 SHA-256과 동일: **통과**

원본 `EUC28-0.wtm` no-op SHA-256:

## 남은 런타임 게이트

1. 텍스트 카탈로그에서 아직 표시될 모든 일본어 코드쌍을 수집해 예약 목록을 만든다.
2. 확정 번역 코퍼스에서 고유 한글 집합을 만들고 영구 코드북을 생성한다.
3. `system.vol` RTDP 사본에 수정 WTM을 재삽입한다. 아카이브 도구의 no-op round-trip이 먼저 통과해야 한다.
4. 알려진 짧은 메뉴/대사 한 줄을 코드북 바이트로 바꾼 파일럿을 Dolphin에서 실행한다.
5. 다음을 캡처로 확인한다.
   - 두 바이트가 한 글리프로 처리되는지
   - 페이지 경계(`B1AC` 등) 글리프 선택이 맞는지
   - 행간/기준선/22 px 전진폭
   - 밝기와 검정 외곽선
   - 문장부호/ASCII 혼합
   - 줄바꿈 및 창 폭 초과

정적 분석과 인코더 검증은 완료됐지만, 최종 한글 글꼴 채택은 이 Dolphin 파일럿 캡처가 통과한 뒤 확정하는 것이 안전하다.
